# Restaurants: reservations redesign — 15 November 2026

Implemented on Web and Business: three scoped tabs, complete pending/upcoming counts, paginated cards, reference/date/status filters, a bounded arrivals sidebar, calendar day counts, and a desktop side panel/mobile dialog with recorded status history. The existing fullscreen shell is retained. FR/EN/LN/SW labels use the existing locale selection.

The new private reservation workspace projection reuses the seller and establishment-owner authority. Queries are bounded (20 rows by default, maximum 50); calendar counts aggregate one local month. Guest projection contains only the account display name, never telephone/address/account identifiers. History exposes the last 20 recorded states/times. Upcoming includes accepted/arrived visits from the current restaurant-local day onward; past and terminal records retain their actual state. No inferred no-show state or seating availability is introduced.

Actual intake requirements distinguish intentional pause from missing seated service, hours, timezone, publication or access. Failed reads remain errors, not setup diagnoses. Existing records remain authorized through the outstanding-work rule. Access capacity means feature entitlement, not seats. Configuration uses the existing profile/hours destinations and revisioned setting operation.

Accept/refuse/cancel/arrive/complete reuse authoritative transitions, revision checks, idempotency keys and the existing notification outbox. Confirmation does not allocate a table, guarantee seats or create an order, invoice or payment. Network-uncertain responses retain the exact command for retry. An updated/stale request refreshes from the server. Customer notification transport/policy is unchanged; no real messages or production records were used in tests. Existing WhatsApp web destinations and reservation query links are retained.

Validation: the targeted reservation suite passed 51 tests, with 2 existing skips; the final workspace suite passed all 8 cases after HTTP/privacy/history checks were added. Coverage includes personal/organization permissions, retained access while intake is paused, pagination/counts, local-midnight boundaries, expiry, no-store responses and existing transition/notification semantics. Web browser checks passed 23 unique cases: four languages at 320/375/390/820/1440 widths plus confirm/refuse/filter/calendar, lost-response retry/partial-load failure, and fullscreen fallback/detail-history preservation. Three Web contract/calendar unit tests and 49 Business gateway/calendar tests passed. Targeted lint, TypeScript and both production builds passed. Desktop/mobile screenshots are preserved in C:/NIHILOBA/release-evidence/restaurant-seven-20261114.

Limitations: Docker was unavailable, so database tests used the existing isolated SQLite fixture; PostgreSQL timezone aggregation and true concurrent database transactions were not verified locally. Business uses the same adapted UI but browser fixtures ran against Web. Current reservation records do not store a customer note or distinguish web/WhatsApp origin; no values were invented. Arrival/completion exist, no-show recording does not. Native-speaker review of Lingala/Swahili remains advisable. No migration or new dependency is required.
