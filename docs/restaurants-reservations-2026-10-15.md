## Workflow and contract

Reservations opens on a phone-friendly list: pending requests first, today's accepted visits second, then upcoming and past reservations. Each row shows the establishment-local date and time with its IANA zone, party size, status, a copyable `RRS_` reference, the response deadline when actionable, and Accept or Decline where the Backend permits a response. Existing Cancel, Record arrival, and Complete visit actions remain available at their Backend-defined states and times. The owner confirms either decision in a focused dialog. An uncertain response keeps its exact operation key for retry; a revision conflict requires refreshing the current state. Successful responses update visible rows and refresh the protected Backend reads. Search by reference and status/local-date filters apply to loaded rows; history is explicitly paginated.

The shared `ShidaCalendar` remains the planning tab. Its month range is the protected Backend calendar read with establishment-local inclusive/exclusive dates; its day agenda opens the same reservation detail. The list is the default. The page displays closed intake and unmet prerequisites, links to the existing establishment profile and hours settings, and still exposes the existing reservation intake switch only where the selected profile has `eat_there` and the capability read includes `restaurant.reservations`. The Backend remains authoritative for publication, hours, seated mode, entitlement, exact ownership, and revisions. Existing obligations remain visible when new intake closes. The establishment type/name is never used as an eligibility shortcut.

The seller DTO intentionally has no guest name, `customer_ref`, source channel, or WhatsApp message ID. The `RRS_` reference is the safe guest identifier. Accept and Decline invoke only the protected reservation transition. No food order, table assignment, advance, bill, payment, or capacity promise is created. The public site and WhatsApp both create the same reservation request. The Backend records a revisioned event and notice; the customer can read the updated status on the public site's authenticated reservation page or through WhatsApp's My reservations choices. WhatsApp delivery is deferred outside its conversation window, and a durable notice/attempt reference prevents duplicate provider sends after ambiguous retries. The Website keeps the same response operation key when the result is uncertain. The Backend's request and action replay checks, choice binding, message references, four-language catalog, and recipient authorization were not changed.
